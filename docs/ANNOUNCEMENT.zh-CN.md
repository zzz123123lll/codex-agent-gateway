# Codex Agent Gateway：让规划验收与实际执行各司其职

当一个 AI 写完代码后说“完成了”，谁来确认它真的完成了？如果所有实现、调试和验收都交给同一个模型，检查很容易沿用它自己的假设。另一方面，有限的 Codex 额度也不必花在每一次文件修改和重复执行上。

**Codex Agent Gateway 把任务组织成两种角色：Codex 负责规划、监督和独立验收，TRAE CN / WorkBuddy 负责使用自己的模型和工具完成实际工作。** 它是运行在 Windows 本机的社区项目，通过 MCP、技能与执行端适配，把两边连接成一个可返工的任务流程。

仓库：https://github.com/zzz123123lll/codex-agent-gateway  
下载：https://github.com/zzz123123lll/codex-agent-gateway/releases/tag/v0.3.1

## 两个出发点

**执行者不应该独自决定自己是否合格。** 可以把更擅长规划和判断、也更受你信任的模型放在监督端，让它先制定要求，再独立运行检查。项目的默认分工选择 Codex 做监督，桌面执行端交付成果；执行结束与正式验收是两个不同状态。

**把 Codex 额度集中用在判断上。** TRAE CN / WorkBuddy 已能用自己的工具编辑文件、运行命令和调试，适合承担大量实现工作。网关让 Codex 在派工、检查和修复指示中发挥作用。节省比例取决于任务、模型、返工次数和产品计费，本项目尚未做定量对照，因此不宣传固定节省百分比。

## 它怎样完成一个任务

Codex 写清需求和验收标准，把任务交给所选执行端。执行端在指定项目中实施并提交文件、命令日志和结果；Codex 检查成果，发现问题时给出具体修复指示，回到同一任务和原生会话继续执行。修复后再检查，达到标准才明确验收。

这个流程支持一次任务内的多轮修复。网关保存轮次、原生身份、事件和成果摘要；超时或状态不确定不会直接变成成功。原生工具权限仍遵循桌面产品自己的审批机制。

## 已经验证了什么

0.3.0 → 0.3.1 的实际验证重新下载并固定了三个 GitHub 项目，构建了三个不同难度的验证应用：

|项目|实际交付|执行端|Codex 冻结业务检查|
|---|---|---|---|
|slugify|多语言 slug CLI、参数与冲突处理|WorkBuddy|21/21|
|p-limit|并发任务执行器、API 与 CLI|TRAE CN|37/37|
|lowdb|可持久化 HTTP 应用、并发和失败写入处理|WorkBuddy|52/52|

**110 项独立业务检查最终通过，三个任务均正式验收；网关自身自动回归另有 113 项通过。** 测试过程实际发现了参数校验、交付证据、持久化一致性以及网关回报与恢复问题，并经过具体返工和复验。这里的结论是“三个固定项目验证应用的功能验收”，并非把整个上游项目或任何复杂产品都重新实现了一遍。

原始上游脚本仍有 Windows 环境相关失败，这些失败与等效检查分别保留；宣传没有把非零退出记录改写成成功。[完整报告](REAL-PROJECT-VALIDATION.md) 和 Release 中的脱敏证据包可供核对。

## 适合谁

适合同时使用 Codex 与 TRAE CN / WorkBuddy、希望把实现与验收分开、需要保留返工和交付证据的 Windows 用户，也适合研究监督型多 agent 工作流的开发者。

当前版本支持这两个桌面执行端，模块结构可继续适配更多 agent；尚未验证任意两个 agent 通用互联。真实验证覆盖一台 Windows 电脑，没有多机或 24 小时无人值守结论。TRAE 迟到报告观察补丁通过离线回归，但该补丁未在本轮实际安装扩展上验证；WorkBuddy 默认配置根范围和桌面版本也已在文档中标明。
