# 常见问题

[返回项目介绍](../README.md) · [安装指南](installation.md) · [验证记录](validation.md) · [完整发布介绍](ANNOUNCEMENT.zh-CN.md)

## 它解决什么问题？

让 Codex 规划并独立检查，让 TRAE CN / WorkBuddy 实际执行。一份交付可以经过多轮“执行 → 检查 → 具体返工 → 复验”，最后留下正式验收与证据。执行者自述完成后，仍要由监督端核验。[来源：任务契约、[架构](ARCHITECTURE.md)]

## 能在一次任务里不断修复，直到交付吗？

可以按已授权目标持续完成这个闭环。返工保留原任务和原生会话，每轮的成果与检查分别记录。相同问题连续两轮没有进展时，应先诊断并调整指示；权限、环境或模型能力阻塞仍需实际解决，不能靠重复轮次自动验收。[来源：[agent-executor](../skills/agent-executor/SKILL.md)、返工源码]

## “执行完成”和“验收完成”有什么区别？

`completed` 表示执行端结束并提交符合格式的结果。`accepted` 表示 Codex 已独立检查本轮真实成果，并保存验收意见和证据。新一轮返工会清除旧验收；执行端的自检报告不替代这一步。[来源：任务状态与验收源码]

## 现在支持任意两个 agent 吗？

当前提供的是 Codex 监督端与 TRAE CN / WorkBuddy 两个原生执行端。MCP、SDK 和 provider 分层是扩展入口；其他 agent 需要实现并验证相应适配。国际版 TRAE 也未在本轮验证。[来源：provider 注册源码、[验证范围](validation.md)]

## 能节省多少 Codex 额度？

目前没有测得节省比例。设计上，把大量编码和命令执行放到桌面执行端，把 Codex 集中用于规划、独立审查和验收。执行端也可能有自己的额度或费用，实际消耗需要结合任务和模型分别测量。[来源：项目设计；额度效果暂无实测数据]

## 可以选择国产模型吗？

执行模型由 TRAE CN / WorkBuddy 的产品配置决定。你先在执行端选择其支持的模型，网关沿用该选择，使用其自身工具完成工作。模型清单、价格和可用性请以相应产品当前界面为准。[来源：执行适配与技能；模型清单未由本项目核验]

## 单独安装 skill 就能用吗？

需要完整网关、MCP 连接和相应桌面执行端。skill 描述协作流程，本身不能连接桌面、持久化任务或验证回报。源码与发布包的安装入口均为 `scripts/setup.ps1`。[来源：[执行技能](../skills/agent-executor/SKILL.md)、安装脚本]

## 安装会修改哪些内容？

正式安装会安装项目依赖、编译和打包，添加名为 `trae-gateway` 的 Codex MCP，复制两个 executor skills，并注册和启动当前用户的登录启动观察任务。TRAE CN 会安装本项目桌面桥并写入桥配置；WorkBuddy 会保存本地执行端配置。先用 `-CheckOnly` 查看预检查结果，具体入口见[安装指南](installation.md)。[来源：setup、install 和 manage 脚本]

`trae-gateway` 这个 MCP 名称保留了兼容入口，仍可提供 WorkBuddy 的执行工具。[来源：安装脚本、MCP 工具与 provider 注册源码]

## WorkBuddy 为什么要先正常退出再安装？

本地连接需要 WorkBuddy 启动时启用对应本机端口。已经打开但没有该端口的实例不能直接接入；先完成工作，通过 **About → Quit WorkBuddy** 正常退出，再安装或按[指南](installation.md)启动。[来源：WorkBuddy 启动与连接源码]

## 它会自动处理工具审批吗？

登录、目录信任和工具审批沿用执行端原生流程，由用户处理。委派任务不会扩大授权。遇到待审批时应查看对应执行会话；看不到按钮或界面与状态不一致时，需要诊断连接和原生状态，保留当前任务，不因超时重复派工。[来源：执行技能、状态协调；新版 WorkBuddy 接口问题见[验证记录](validation.md)]

## 能长期无人值守吗？

服务有登录启动观察和进程退出后的重新启动机制，任务和原生身份会持久化。但本轮没有第二台电脑或 24 小时以上无人值守的实测证据，也没有覆盖所有卡死、断电或产品升级情况。当前结论是单台 Windows 的真实项目闭环通过。[来源：生命周期源码、[验证范围](validation.md)]

## 三个真实项目到底测了什么？

在固定 GitHub 源码上新增了多语言 slug CLI、并发批处理与 CLI、持久化 HTTP 应用。Codex 派工前冻结的独立检查分别为 21、37、52 项，最终 110/110 通过并正式验收。网关自动回归 113/113、报告辅助回归 10/10 是另外两组检查；执行端自检、补充代码审查与历史测试均不混入 110 项。[来源：冻结检查、回归与验收记录]

验证期间保留了原始失败、具体返工与复验。部分上游 Windows 测试、lint 或 build 存在环境限制；直接检查和等效检查成功不会改写原始退出码。详见[验证说明](validation.md)。[来源：原始运行与验收证据]

## 支持哪些版本与配置？

本轮实测为 Windows、Node.js 24.15、TRAE CN 3.4.2、WorkBuddy 5.7.7；最低 Node.js 要求为 22.13。WorkBuddy 默认配置根下的托管 Node 已做原生身份验证，自定义配置根未自动支持。桌面产品升级后需要重新验证接口。TRAE 迟到回报观察新桥补丁在本轮仅有离线回归，未安装进行原生迟到恢复实测。[来源：安装预检查、[部署与验证范围](validation.md)]

## 它是官方产品吗？采用什么许可证？

这是独立项目，没有 OpenAI、TRAE 或 WorkBuddy 官方背书。当前发布实现采用 [MIT](../LICENSE)，依赖保留各自许可证。早期研究与沿用历史、当前重写范围保留在 [PROVENANCE](../PROVENANCE.md)与 [NOTICE](../NOTICE.md)；重写记录不等于法律意义上的净室或第三方授权认证。[来源：许可证、来源记录]

## 怎样反馈问题？

在 [Issues](https://github.com/zzz123123lll/codex-agent-gateway/issues) 提供网关版本、执行端版本、重现步骤、期望与实际结果，以及脱敏日志。遇到执行不确定或取消未确认的任务，优先保留原任务和会话；报告时移除令牌、账号信息和私人路径。[来源：项目支持流程、身份协调与技能]
